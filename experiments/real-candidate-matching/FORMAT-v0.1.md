# 创作推荐数据契约 v0.1

2026-10-26。冻结范围是原型与下一轮使用流程之间的数据接口，不表示全库已经迁移或文学分类已经定论。保留原始知识文档，在其上增加少量可审核的结构标注。

## 1. 三份数据分开保存

| 数据 | 归属与作用 | 主要内容 |
| --- | --- | --- |
| 原始知识及结构目录 | 跨项目共享 | 母题、情境、技巧的定义、条件、阶段或可选操作、原文来源 |
| 项目允许前文与候选 | 每部作品独立 | 截点内场景、候选命题、角色标识、具体角色与物件绑定 |
| 审核与推荐产物 | 绑定项目版本及截点 | 事实和知情判断、事件发生位置、适用状态、待选计划 |

母题库案例和结局不能进入作品历史事实；推荐方案也不能自动变成已发生事件。

## 2. 项目与命题

沿用 `schema_version: 1` 的项目结构：`project_id / characters / pov_character / scenes / facts / threads / goal`。场景包含唯一 `id`、叙述顺序 `order` 与原始解码文本。字符位置一律为 Unicode 字符半开区间 `[start,end)`，不是字节。

`scene.order` 只表示正文叙述位置，不能单独证明故事时间顺序。传给候选准备器的全部场景都会被视为允许前文，因此调用者必须先选定或截断前文。真实实验先核对源书哈希与前文的唯一连续位置，再提供冻结的局部片段。

角色键在一个项目内唯一；同名角色不跨项目共享知情。化名使用同一角色键，不因为出现新名字就新增一个人。本轮原创样例的“季衡／阿川”属于同一角色，自动别名解析尚未实现。

命题类别与知情关系分开：

- `content`：内容本身，例如暗号值。
- `carrier`：载体或来源相关命题，例如某封信记有暗号；寄件者另为命题。
- `acquisition_event`：读到、收到、理解等获取事件。
- `communication_event`：写下、说出、转告等传播事件。
- `world_state`：其他状态或条件。

类别是当前标注，不能替代审核。“甲说过 X”可以成立，而 X 仍可能只是猜测。复合命题中只要一部分缺少依据，整条不自动通过；尽量把可独立变化的内容、载体、工具持有与用途知情拆开。

## 3. 共享知识条目

目录仍使用 `motifs` 作为兼容的集合键；每项必须保留稳定 `id`，并用 `knowledge_kind` 明确为 `motif / technique / situation`。省略时兼容旧目录，默认 `motif`。输出必须保留类型，不能把技巧适用称为母题命中。

| 字段 | 含义 |
| --- | --- |
| `source.path / sha256 / evidence` | 原文件与精确引文；来源文本和我们设计的运行规则分别保存 |
| `roles` | 角色或物件槽位，角色必须属于该项目 |
| `conditions` | 稳定条件编号、完整命题模板、命题类别 |
| `entry_conditions` | 所有操作共同需要的条件 |
| `stage_mode` | `progression` 为进展阶段；`alternatives` 为相互独立的操作入口 |
| `stages` | 每个阶段／入口需要的条件；`chronological` 为事件条件列表，无顺序要求时填 `[]` |
| `variants` | 对应阶段／入口的后续提案及附加条件 |
| `operationalization_note` | 哪些来自资料，哪些是本轮设计，以及适用范围 |

`progression` 选最后一个证据完整的阶段。若角色已知更后面的事件完成、但次序未确认，不回退去建议重复动作。

`alternatives` 不把列表位置解释成时间或优先级。任何证据完整的入口都可给出方案；另一入口未知不取消已经满足的入口。例如“沿未解疑点观察”和“核对已说出的试探判断”可以属于同一技巧的两个入口。

## 4. 条件实例与审核上下文

`prepare_candidates(project,catalog,instances,repo_root)` 生成派生项目和审核包。每个实例包含 `id / motif_id / bindings / anchors`。一个上下文锚点只有 `scene_id / start / end`；程序从允许正文提取原文，填入条件模板，生成待审核命题。

锚点只说明审阅时可以参考哪段文字，不证明条件成立。生成命题标为 `unreviewed_condition_probe`；列出的知情角色同样是待审主张。缺少锚点时，该条件保持未绑定和未知，不补造原文，也不把“不知道”改成“为假”。

实例命题与填入角色后的模板必须逐字一致，避免将“拿到载体”重新贴成“理解内容”。准备器不修改输入项目，派生项目也不自动写回正式记忆。

## 5. 语义与时间审核

继续使用 `semantic_review` 的项目、前文包、审核绑定：`project_sha256 / packet_sha256`。知识目录摘要参与派生项目版本，修改条件或绑定后旧审核不能直接套用。

每条候选分别审核：`verdict = supported / contradicted / insufficient_evidence`；`epistemic_type = established / reported / inferred / uncertain`；每个角色另有知情判断。带支持或反证的判断必须提供精确允许原文。

只有“支持＋确定事实＋当前角色知情有支持”进入视角事实。传闻和推断不升级为世界事实；缺审保持未知。若一个已审核命题只是言说事件，则可使用“某人提出了什么”，不能直接使用其内嵌答案。

需要事件次序的阶段还要有 `event_anchor` 与 `chronology_review`。事件锚点必须是同一判断的证据，说明事件在该处实际发生；不能使用计划、回忆或候选最初附带的引文位置代替。锚点重叠或顺序证据不足时保留未知，明确逆序则不通过。

状态适用性不等于事件顺序已经得到验证。本轮原创对照含回溯内容，全局正序审核保留不足，未将其当成顺序衔接成功案例；无需时间次序的当前状态条件仍可分别检查。

## 6. 输出与成品接口

作者核对视图包含：`entry_status`（共同前提）、`applicability_status`（是否存在成立的阶段／入口）、`supported_stage_ids`、支持／反证／未知条件，以及每项证据。类型和状态分别显示，不设文学质量概率或强制唯一赢家。

`writer_packet` 只包含 `facts` 和 `proposals`。实验还补入当前视角已审核的具体原始事实，让“答案已确认”旁边确实有答案内容。审核理由、隐藏事实、缺条件的猜测不进入写作包。`writer_prompt` 直接由该包构造，提案保持待选择状态。

下一轮产品流程使用这些接口完成：导入前文 → 审核派生状态 → 查看候选与依据 → 选择并编辑提案 → 作者确认后更新本项目记忆。确认前不自动写回。当前 AI 审阅可以继续作为审核提供者，未要求新增付费接口。

本轮不冻结全库文本写法、自动召回算法或错误信念模型；这些不应成为下一轮做出完整使用流程的前置条件。
